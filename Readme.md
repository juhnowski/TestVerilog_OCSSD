# Проектирование контроллера Open-Channel SSD (OCSSD)

- https://github.com/chili-chips-ba/openPCIE - Совсем свежий полностью открытый проект контроллера PCIe (включая Transaction и Data Link уровни) для тех, кто хочет уйти от проприетарных блоков вендоров

## 2. Уровень NVMe (Протокол и Команды)
- https://github.com/enjoy-digital/litenvme - Часть экосистемы LiteX. Позволяет развернуть компактный хост/таргет контроллер. Он написан на Python-подобном HDL (Migen/LiteX), но генерирует чистый, готовый к интеграции Verilog.
- https://github.com/yu-zou/DirectNVM Открытый RTL-контроллер NVMe, специально оптимизированный для работы на FPGA без участия встроенного процессора

# Архитектура Open-Channel SSD на FPGA
```text
  [ Хост (Linux / LightNVM) ] 
               │  (Физическая шина PCIe)
  ┌────────────▼────────────────────────────────────────┐
  │ FPGA Контроллер OCSSD                               │
  │                                                     │
  │  ┌──────────────────────┐     ┌──────────────────┐  │
  │  │  verilog-pcie (DMA)  │◄───►│  NVMe Core       │  │
  │  └──────────────────────┘     │  (Парсер команд) │  │
  │                               └────────▲─────────┘  │
  │                                        │            │
  │  ┌─────────────────────────────────────▼──────────┐  │
  │  │ Ваш кастомный модуль: Open-Channel Геометрия   │  │
  │  │ (Отображение очередей на физические Flash-каналы)│  │
  │  └─────────────────────────────────────┬──────────┘  │
  └────────────────────────────────────────┼────────────┘
                                           │  (Интерфейс ONFI / Toggle)
                              [ Чипы Флеш-Памяти (NAND) ]
```                              
- Front-end (PCIe + DMA): Принимает пакеты (TLP) из шины компьютера, организует кольцевые очереди (Submission/Completion Queues) в оперативной памяти хоста через DMA.
- Protocol Engine (NVMe): Разбирает стандартные команды (Read, Write, Identify). В случае Open-Channel SSD версии 2.0 (OCSSD 2.0) контроллер должен поддерживать Physical Page Addressing (PPA) Command Set. То есть хост отправляет не абстрактный LBA (логический адрес), а конкретный PPA, кодирующий: [Канал][Кристалл][Блок][Страница]
- Back-end (Flash Controller): Ваш собственный модуль, который принимает физическую команду от NVMe-движка и дергает ножки интерфейса NAND-памяти (ONFI или Toggle DDR) для чтения или записи конкретной ячейки.

# Разбираемся с DMA для OCSSD
Хост (сервер) сообщает контроллеру, куда писать данные. В NVMe это происходит через дескрипторы в очередях.

## Структура DMA дескриптора:
- address (64 бит) — физический адрес в оперативной памяти сервера.
- length (32 бит) — сколько байт нужно передать.
- tag (8-16 бит) — идентификатор транзакции, чтобы не запутаться в ответах.

# Карта регистров NVMe (Register Map)
Первое, что делает хост (драйвер Linux LightNVM / NVMe) при инициализации SSD — это опрашивает его конфигурационное пространство PCIe и мапит базовый адрес регистров (BAR0) в свою оперативную память.Ваш контроллер должен обрабатывать эти транзакции. Самый важный интерфейс здесь — AXI-Lite. Ядро verilog-pcie, которое вы склонировали, берет на себя всю физику PCIe и выдает вам чистый мастер-интерфейс AXI-Lite (сигналы адреса, данных и стробы записи).
## nvme_regs.v - RTL-код Doorbell Registers
модуль будет декодировать адреса от verilog-pcie и ловить моменты, когда хост пишет в Submission Queue 0 Tail Doorbell (сигнал «я положил новую команду в Admin-очередь, забери её по DMA»).
Тест: `tests.test_nvme_regs.test_doorbell_write`

# Submission Queue Entry
Что происходит дальше по спецификации NVMe и Open-Channel 2.0?
Когда хост (сервер) записал в наш Doorbell регистр значение 5, он сообщил аппаратуре: 
```
В оперативной памяти сервера теперь лежит 5 команд. Забери их
```
Каждая команда NVMe имеет фиксированный размер — 64 байта (__Submission Queue Entry, SQE__). 

Наш контроллер должен:
- Запустить DMA-чтение из RAM сервера, используя физический адрес очереди.
- Вычитать эти 64 байта.
- Распарсить их, чтобы понять, какая именно операция (чтение, запись или специфическая для Open-Channel команда геометрии) от нас требуется.

Команды ввода-вывода используют формат __PPA (Physical Page Address)__ вместо LBA.

## Структура 64-байтной команды в Open-Channel SSD:
- Dword 0: OPC (Opcode, 8 бит) — код операции (например, 0x01 — запись, 0x02 — чтение, 0x91 — кастомный Open-Channel Reset Vector/Chunk).
- Dword 1: NSID (Namespace Identifier, 32 бита) — идентификатор пространства имен.
- Dword 10-11: MPTR (Metadata Pointer, 64 бита) — адрес для метаданных.
- Dword 12-13: PRP1 и PRP2 (Physical Region Page, по 64 бита) — указатели на физические страницы в ОЗУ сервера, откуда нужно забрать или куда положить данные (самый важный элемент для DMA!).
- Dword 14-15 (Специфика OCSSD): Физический адрес страницы (PPA). Драйвер передает его прямо в этих полях:
    - Группа (Channel) — 8 бит
    - PU (LUN/Die) — 8 бит
    - Chunk (Block) — 16 бит
    - Page — 16 бит

## nvme_parser.v - RTL-код парсера команд
Фронтенд контроллера теперь официально умеет делать две важнейшие вещи: принимать сигналы управления от драйвера (Doorbell) и считывать сложную 64-байтную геометрию команд Open-Channel SSD (PPA).

# Топ-модуль контроллера OCSSD
Теперь нам нужно объединить декодер регистров (nvme_regs) и парсер команд (nvme_parser) в единую систему верхнего уровня — src/ocssd_top.v.

В реальном устройстве между ними будет находиться DMA-движок (из репозитория verilog-pcie), который по сигналу admin_sq_tail_update забирает команду из памяти сервера и передает её в nvme_parser. В нашем топ-модуле мы заложим эту управляющую логику (простой автомат состояний — FSM), который будет координировать вычитку.
```
[Хост / Драйвер] 
      │ (AXI-Lite)
      ▼
┌───────────────┐  tail_update  ┌────────────────────┐
│   nvme_regs   ├──────────────>│ Контроллер / FSM   │
└───────────────┘               └─────────┬──────────┘
                                          │ (Запуск DMA)
                                          ▼
┌───────────────┐   cmd_data    ┌────────────────────┐
│  nvme_parser  │<──────────────┤  Память / Хост     │
└───────┬───────┘   (512 бит)   └────────────────────┘
        │
        ▼ (Выходы PPA: Канал, Кристалл, Чанк, Страница)
 [К Flash-памяти]
 ```

 ## ocssd_top.v
 Теперь у вас есть полноценная база для разработки аппаратного обеспечения: автоматический запуск тестов, контроль иерархии топ-модуля и генерация временных диаграмм. Весь базовый конвейер управления (Register Map -> Parser -> Top FSM) работает без сбоев.

 # Архитектура Арбитража Очередей (Queue Arbiter)
 В нашем контроллере мы реализуем схему Round-Robin (круговой арбитраж) между двумя очередями:
 1. Admin Submission Queue (Admin SQ): Очередь для системных команд (управление, геометрия OCSSD, создание I/O очередей). Имеет наивысший приоритет.
 2. I/O Submission Queue 1 (I/O SQ1): Высокоскоростная очередь для кастомных команд ввода-вывода (чтение/запись по PPA-адресам флеш-памяти).

 ## Логика автомата состояний (FSM) арбитра:
 - IDLE: Ожидание флага обновления звонка (update). Если звонок зафиксирован, переходим к арбитражу.
 - ARBITRATE: Выбор активной очереди. Если активны оба звонка, Round-Robin или фиксированный приоритет выбирает нужную очередь.
 - FETCH_CMD: Формирование запроса DMA Read Descriptor к ядру verilog-pcie. Передаем физический базовый адрес очереди хоста + смещение хвоста.
 - WAIT_DMA: Ожидание завершения транзакции чтения (сигнал готовности данных от шины).

 ## src/queue_arbiter.v
 Этот модуль отслеживает состояние указателей хвоста очередей (Tail) и формирует дескриптор чтения для DMA-интерфейса verilog-pcie.

 # DMA Data Mover (Буферизация команд)
 Теперь, когда арбитр очередей выдает ядру verilog-pcie правильный физический адрес дескриптора (dma_read_desc_addr), нам необходим узел, который встретит эти данные с шины PCIe. По спецификации NVMe, считанная 64-байтная команда падает во внутренний буфер контроллера.Нам нужно реализовать `src/dma_data_mover.v`. 
 
 Его задачи:
 1. Принять 512-битный поток данных (64 байта) от интерфейса передачи данных ядра.
 2. Сохранить его во внутренний регистровый FIFO-буфер.
 3. Выдать сигнал валидности для нашего nvme_parser

 ```text
        [verilog-pcie DMA Channel]
                   │
                   ▼ (dma_cmd_data / dma_cmd_valid)
┌──────────────────────────────────────┐
│           dma_data_mover             │ <--- Наш новый блок
└──────────────────┬───────────────────┘
                   │
                   ▼ (Внутренняя шина 512 бит)
┌──────────────────────────────────────┐
│             nvme_parser              │
└──────────────────────────────────────┘
```

`test_dma_mover.py` - нужно убедиться, что буфер корректно защелкивает широкую 512-битную шину данных и удерживает сигналы управления в соответствии с протоколом AXI-Stream / Handshake.

# Flash Interface
Спуск на физический уровень (Flash Interface) позволит нам замкнуть цепочку от звонка драйвера хоста до реальных таймингов микросхем памяти.
Мы спроектируем канальный контроллер, соответствующий базовому стандарту __ONFI (Open NAND Flash Interface)__. 
Его задача — принять логические сигналы геометрии (flash_channel, flash_page, чанк, лун), переключить стейт-машину шины NAND и выдать точные сигналы на физические пины: CLE (Command Latch Enable), ALE (Address Latch Enable), WE# (Write Enable), RE# (Read Enable) и двунаправленную шину данных IO.

## Архитектура ONFI-контроллера (Канальный уровень)
Стандартная операция записи страницы (Page Program) в NAND Flash состоит из трех фаз:
1. Команда 80h (Serial Data Input): Выставляется CLE=1, на шину IO кладется байт 80h, дергается WE#.
2. Адрес (5 циклов): Выставляется ALE=1. В течение 5 тактов WE# передаются: столбец (2 байта, внутри страницы) и строка (3 байта: страница, блок/чанк, LUN).
3. Данные и Команда 10h (Program Confirm): Передаются байты данных страницы, затем CLE=1, на шину IO кладется 10h, и память уходит в состояние Busy (сигнал RB# падает в 0).

`src/onfi_chan_ctrl.v` - этот модуль реализует логику выдачи циклов Команда/Адрес/Данные с учетом базовых протоколов ONFI.
`test_onfi_ctrl.py` -  тест, симулирующий подачу геометрии. Мы проверим, выдерживает ли стейт-машина диаграмму: строб CLE с байтом 80h, затем переход в ALE на 5 тактов с выдачей адреса страницы/чанка, и завершение байтом 10h

# Двунаправленная шина IO (Бинаправленный буфер)
В симуляции мы проверили фазу выдачи команды и адреса (когда данные летят из контроллера в чип, nand_io_dir = 1). Но в реальном NAND Flash шина nand_io является двунаправленной (inout). Когда хост запрашивает чтение страницы, память выдает данные на те же самые ноги, и контроллер должен переключить nand_io_dir = 0.В 

Verilog для этого используется конструкция трех состояний (тристат Z):
```verilog
assign nand_io = (nand_io_dir) ? nand_io_out : 8'hZ;
assign nand_io_in = nand_io;
```
Для того чтобы симулировать чтение (например, чтение байта статуса 70h из Flash, чтобы проверить, завершилась ли запись страницы в NAND), нам нужно:
1. Дописать фазу чтения статуса в стейт-машину onfi_chan_ctrl.v.
2. Реализовать тристатный буфер на шине nand_io

По спецификации ONFI, после команды подтверждения программы (10h) память уходит в состояние Busy. 
Чтобы узнать, завершилась ли физическая запись во флеш-матрицу успешно, контроллер должен:
1. Выставить CLE = 1, положить на шину команду 70h (Read Status).
2. Переключить шину данных на вход (nand_io_dir = 0).
3. Опустить строб чтения RE# = 0 и считать байт статуса.
4. Проверить Бит 0 (0 — Успех, 1 — Ошибка записи/Write Fault) и Бит 6 (1 — Кристалл готов, 0 — Кристалл занят).

## RTL-код ONFI Контроллера с поддержкой inout
Перепишем src/onfi_chan_ctrl.v. Мы заменим порт output wire [7:0] nand_io_out на честный inout wire [7:0] nand_io и добавим фазы чтения статуса в автомат состояний (FSM)
